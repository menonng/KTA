## 1. 목표와 제약 (측정 가능한 숫자로)

### 1.1 메모리: 목표 300MB, 상한 400MB

- 2026년 측정 자료에 따르면 가벼운 페이지 탭 하나의 상주 메모리는 약 76MB(위키백과)~110MB(해커뉴스)다.
- Tom's Guide 테스트에서는 크롬 탭 10개가 952MB였다(탭당 약 95MB).
- 따라서 **크롬 탭 5개 ≈ 400~500MB**로 본다. 보수적으로 가벼운 탭을 기준으로 잡았다.

| 구분 | 목표 | 상한 |
|---|---|---|
| 게임 전체(탭 렌더러 프로세스 + GPU 프로세스 몫) | **300MB** | **400MB** |

> ⚠️ 내장 GPU에는 별도 VRAM이 없고 시스템 RAM을 나눠 쓴다. 텍스처와 버퍼가 곧 RAM 사용량이다. 반실사 PBR은 재질 하나에 텍스처가 3장(색, 노멀, 거칠기/금속/AO)씩 들어가므로 **텍스처 예산 관리가 이 프로젝트의 핵심**이다.

### 1.2 GPU: 외장 그래픽 없이

| 등급 | 예시 기기 | 목표 |
|---|---|---|
| 최저 | Intel UHD 620 (8세대 i5 노트북, RAM 8GB) | 1080p, 렌더 배율 0.75, **30fps 이상** |
| 표준 | Intel Iris Xe / AMD Radeon 내장(Ryzen 5000U급) | 1080p, **60fps** |
| 표준 | Apple M1 (RAM 8GB) | **60fps** |
| 참고 | 중급 안드로이드·아이폰(인스타·스레드 인앱 브라우저) | '낮음' 프리셋, 30fps |

### 1.3 CPU

- 표준 기기 60fps에서 **CPU 전체 사용률 25% 이하**(4코어 기준 약 1코어). 절전 모드(30fps)에서는 15% 이하.
- 탭이 비활성이거나 일시정지 중이면 사실상 0%.
- 120/144Hz 모니터에서도 **60fps로 캡**한다.

### 1.4 로딩

- 첫 플레이까지 다운로드 **15MB 이하**(압축 기준). 장면에 들어갈 때마다 해당 장면 에셋을 받는다(장면당 5~15MB 목표).
- SNS 인앱 브라우저에서 링크를 누르고 LTE 기준 10초 안에 첫 장면이 뜨는 것이 목표다.

### 2.4 해석과 아트 방향

**목표는 "AI 이미지 화질 그대로"가 아니라 "GTA V급 인게임 느낌"이다.** AI 이미지는 오프라인 렌더 수준이라 내장 GPU 실시간 렌더로는 그대로 따라갈 수 없다. 대신 아래 방법으로 느낌을 최대한 가깝게 만든다.

- **미리 구운 조명이 핵심:** 장면이 좁고 대부분 고정된 공간이다. Blender(Cycles)에서 간접광·그림자·AO를 라이트맵으로 구워 두면, 실시간 비용 없이 사실적인 조명을 얻는다. 움직이는 캐릭터와 물체는 라이트 프로브(구면 조화 함수)로 주변 조명을 받는다. 반사는 장면당 큐브맵 1~2개.
- **동적 그림자는 캐릭터 주변만:** 작은 그림자맵(1024) 하나를 캐릭터 주변에만 맞춘다. 정적인 그림자는 이미 구워져 있다.
- **후처리:** AgX/ACES 톤매핑, 저해상도 블룸(간판·조명), LUT 컬러 그레이딩(따뜻한 색감), FXAA/SMAA. SSAO 같은 무거운 화면 효과 대신 구운 AO를 쓴다.
- **사진 모드(바이럴 핵심):** 일시정지한 뒤 한 프레임만 고품질로 렌더한다(슈퍼샘플링, 여러 프레임 누적 안티에일리어싱, 피사계 심도, 고해상도 그림자). **원본 유행 짤과 같은 결과물을 게임이 직접 만들어 주는 구조**다. 고해상도 출력은 타일 단위로 렌더해 메모리 피크를 막는다.
- **스타일:** 실사보다 살짝 과장된 색과 대비. GTA 계열 인게임 렌더의 "느낌"은 반실사라는 일반적인 스타일 범주다. 특정 원작의 캐릭터·로고·UI를 따라 하는 것과는 구분한다(9장).

### 3.3 후보별 근거

**A. Rust만, 네이티브**
- 장점: 성능과 메모리 효율이 가장 좋다. 멀티스레드를 자유롭게 쓸 수 있다.
- 단점: 설치가 필요하다. Windows SmartScreen 경고, macOS 공증 같은 배포 장벽이 있다. **링크를 눌러 바로 하는 경험이 불가능해서** 유행을 타고 퍼지기에 치명적이다.

**B. Bevy → WASM → 웹**
- 반실사 쪽 기능(라이트맵, 반사 프로브, 블룸, 톤매핑, 대기 산란 등)을 엔진이 기본으로 제공하는 점은 강점이다. 다만 compute 셰이더가 필요한 기능은 WebGL2에서 쓸 수 없다.
- 웹 기본 백엔드는 WebGL2이고, WebGPU는 `webgpu` 기능으로 켠다. 켜면 WebGL2 지원을 대체한다(0.16 문서 기준). 그래서 **두 백엔드를 모두 지원하려면 wasm을 두 벌 빌드해야 한다.**
- 바이너리 크기: 2023년 보고로는 단순한 예제도 약 22MB, 크기 최적화를 하면 12MB 이하였다. 오래된 수치라서 Phase 0에서 다시 잰다.
- 릴리스 주기: 0.18(2026-01-13), 0.19(2026-06-19). 릴리스마다 호환성이 깨지는 변경이 있다.
- 웹에서 멀티스레드를 쓰려면 SharedArrayBuffer와 COOP/COEP 헤더가 필요하다. **GitHub Pages는 이 헤더를 보낼 수 없다.**
- 한글: 게임 안의 텍스트를 엔진이 직접 그려야 한다. 한글 완성형은 11,172자라 폰트 파일이 크고 글리프 아틀라스가 메모리를 차지한다.

**B'. wgpu 직접**
- 라이트맵, PBR, 스키닝, 후처리를 전부 직접 구현해야 한다. 1인 개발이라면 렌더러를 만들다가 게임을 못 만든다.

**C. Three.js 단독**
- Three.js는 min+gzip 기준 약 168KB(r175)다. WebGPU 빌드는 노드 시스템이 들어가서 더 크므로 Phase 0에서 측정한다.
- `WebGPURenderer`는 WebGPU가 없으면 WebGL2로 자동 폴백한다. TSL 셰이더는 WGSL과 GLSL 양쪽으로 컴파일된다. 단, compute는 폴백에서 쓸 수 없다.
- 라이트맵 + PMREM 환경맵 + 라이트 프로브 조합은 웹 건축 시각화에서 많이 검증된 방식으로, 이번 장면 구조와 잘 맞는다.
- 단점: 큰 게임 로직을 JS로 짜면 GC 끊김과 구조 관리 부담이 생긴다. Rust 요구도 충족하지 못한다.

**D. Rust 코어 + Three.js (추천)**
- C의 장점을 그대로 가져가면서 게임 로직은 Rust로 쓴다. 렌더러 대안으로는 Babylon.js가 있다(PBR과 디버깅 도구가 강하지만 번들이 약 1.4MB로 크다).

**E. Godot 4 웹**
- Godot 4.3부터 단일 스레드 웹 내보내기가 기본이라 GitHub Pages에서도 돈다. 하지만 멀티스레드보다 느리고, 느린 기기에서 오디오 끊김 문제가 있었다(이후 개선).
- 엔진 런타임 전체를 받아야 해서 초기 다운로드와 메모리 기준선이 크다. 에디터 생산성은 가장 좋다.

**참고: 데스크톱 래핑(Tauri)**
- Windows의 WebView2는 크로미움 기반이라 Electron과 메모리 차이가 작다. 이득이 큰 쪽은 macOS와 설치 파일 크기다.

### 3.4 결론: D를 추천하는 이유

1. **유행 콘텐츠에서는 "링크 탭 → 바로 플레이"가 최우선이다.** 웹 배포가 사실상 필수다.
2. **첫 다운로드가 가장 작다.** 렌더 엔진이 수백 KB라 장면 에셋에 용량을 더 쓸 수 있다.
3. **게임 로직은 Rust로 쓴다.** 시간대, 경제, 활동(미니게임), NPC 일정, 물리, 세이브를 Rust로 짠다. 렌더러를 바꿔도 코어는 그대로이므로 **나중에 네이티브 클라이언트를 붙일 수 있다.**
4. **한글 HUD, 메뉴, 대화창을 브라우저 텍스트 엔진에 맡긴다.**
5. **WebGPU/WebGL2 폴백을 빌드 하나로 처리한다.** Linux·Android Firefox와 인앱 브라우저의 WebGPU 지원이 불확실해서 **WebGL2가 기본 경로**여야 한다.

> **결정 게이트:** 반실사 방향에서는 Bevy의 기본 기능이 매력적이다. 그래서 Phase 0에서 **같은 편의점 장면**을 D와 B로 만들어, 화질(레퍼런스와 나란히 비교)·메모리·CPU·첫 로딩을 실측한 뒤 확정한다.

### 4.2 월드 구조: 허브 + 장면

| 구분 | 예시 | 크기 | 비고 |
|---|---|---|---|
| 거리 허브 | 홍대입구역 앞 느낌의 거리, 성수 느낌의 골목 | 블록 1~2개 | 노점, 가게 입구, 군중. 원경은 배경 카드로 처리 |
| 실내 장면 | 편의점, 원룸, 삼겹살집, 빵집, 옷가게 | 방 1~3개 | 라이트맵 품질을 가장 높게 |
| 전환 | 문, 역 출구 | — | 짧은 페이드 + 이전 장면 해제 → 다음 장면 로드 |

끊김 없는 오픈월드 대신 이 구조를 쓰는 이유:
- 레퍼런스 장면이 모두 좁은 공간이다.
- 장면마다 메모리를 비우고 채울 수 있어 300MB 예산을 지키기 쉽다.
- 장면 단위로 조명을 구울 수 있다.

### 4.3 계층별 책임

| 계층 | 맡는 일 | 맡지 않는 일 |
|---|---|---|
| kta-core (Rust) | 게임 규칙, 물리, NPC 일정, 활동 규칙, 경제, 시간대, 세이브, 장면 전환 판단 | 메시·텍스처·DOM. 에셋은 `asset_id`로만 다룬다 |
| 렌더러 (TS + Three.js) | 씬 그래프, 머티리얼, 라이트맵 적용, 스키닝, 후처리, 사진 모드, 에셋 로드·해제 | 게임 규칙 |
| HUD (DOM/CSS) | 시계, ₩, 상태, 활동 UI, 메뉴, 대화, 사진 앨범 | 3D 렌더 |
| 플랫폼 계층 (TS) | 입력(키보드·게임패드·터치), 오디오, 저장, 페이지 가시성 | — |

### 4.4 Rust ↔ JS 경계 원칙

- **프레임당 호출은 1~2회:** `core.step(dt, input)`, `core.drain_events()`. 개체 단위 호출은 금지한다.
- **복사 없는 변환 데이터:** Rust가 SoA 버퍼를 소유하고, JS는 `Float32Array` 뷰로 직접 읽는다. wasm 메모리가 늘어나 `memory.buffer`가 바뀌면 뷰를 다시 만든다.
- **이벤트:** 고정 크기 링버퍼(활동 완료, 돈 변화, 사운드 트리거, 장면 전환 요청).
- **물리:** `rapier3d` Rust 크레이트를 코어에 직접 넣는다(wasm 하나, 경계 하나).

## 5. 에셋 파이프라인

### 5.1 흐름

```
Blender(.blend 원본)
  ├─ 정적 환경: 라이트맵 UV(2번 UV) → Cycles로 라이트맵·AO 베이크
  └─ 캐릭터: 리깅 → 애니메이션 → 블렌드셰이프
  → glTF 2.0 내보내기
  → gltf-transform: dedup → weld → simplify(LOD) → quantize → meshopt
                    → KTX2 (색·ORM은 ETC1S, 노멀·라이트맵은 UASTC)
  → 장면 단위 .glb + 공용 에셋 .glb
  → CDN
```

### 5.2 텍스처 메모리 계산 (GPU 상주, 밉맵 포함)

| 2048×2048 텍스처 1장 | GPU 메모리 |
|---|---|
| PNG/JPG (디코드 후 RGBA8) | 약 **21.3MB** |
| KTX2 UASTC → BC7/ASTC 4×4 (픽셀당 1바이트) | 약 **5.3MB** |
| KTX2 ETC1S → BC1/ETC (픽셀당 0.5바이트) | 약 **2.7MB** |

PBR 재질 하나(2K 텍스처 3장)를 PNG로 쓰면 64MB다. KTX2로는 약 11~16MB다. **PNG 텍스처는 금지**하고 KTX2만 쓴다.

### 5.3 텍스처 해상도 정책

| 대상 | 해상도 | 비고 |

## 6. 성능·메모리 예산

### 6.1 메모리 예산 (목표 300MB)

| 항목 | 예산 | 수단 |
|---|---|---|
| 브라우저 탭 기본 | 약 80MB | 고정비(1.1절 측정 자료 기준) |
| JS 힙(Three.js 객체, HUD) | 28MB 이하 | 객체 풀링, 프레임당 할당 0 |
| WASM 선형 메모리(코어 + 물리) | 28MB 이하 | 초기·최대 크기 지정, 아레나 할당. **wasm 메모리는 한 번 늘면 줄지 않는다** |
| GPU: 텍스처(현재 장면 + 공용) | 96MB 이하 | KTX2, 해상도 정책(5.3), 장면 전환 시 해제 |
| GPU: 지오메트리(스키닝 포함) | 28MB 이하 | 양자화, 인스턴싱, LOD |
| GPU: 렌더 타깃 | 28MB 이하 | HDR 버퍼 + 깊이 + 블룸 체인. 렌더 배율로 조절, MSAA 대신 FXAA/SMAA |
| 오디오 | 12MB 이하 | BGM·환경음 스트리밍, 효과음만 디코드 |
| **합계** | **약 300MB** | 상한 400MB까지 여유 100MB |

- **장면 전환:** 이전 장면을 먼저 해제한 뒤 다음 장면을 로드한다(페이드 화면 동안). 두 장면이 동시에 메모리에 올라가지 않게 한다.
- **사진 모드:** 고해상도 출력은 타일 단위로 렌더해 추가 피크를 30MB 이내로 묶는다.

### 6.2 렌더 예산 (표준 기기, 60fps)

- **draw call 300 이하/프레임.** WebGL은 호출당 CPU 비용이 커서 CPU 사용률과 바로 연결된다.
- 화면 안 삼각형 60만 이하.
- **조명:** 정적 조명은 전부 구운 조명. 실시간 광원은 2~4개(캐릭터를 비추는 키 라이트 등).
- **그림자:** 캐릭터 주변에만 1024 그림자맵 1장.
- **픽셀 비율 상한 1.0~1.25.** 고DPI 노트북에서 2.0으로 두면 그려야 할 픽셀이 4배가 된다.
- **동적 해상도:** 프레임 시간 p95가 기준을 넘으면 렌더 배율을 1.0에서 0.67까지 자동으로 낮춘다.
- 품질 프리셋 낮음/중간/높음 + 첫 실행 시 자동 감지. '낮음'에서는 블룸을 끄고 라이트맵 해상도를 절반으로 쓴다.

### 6.3 CPU 절약 전략

- 60fps 캡, 절전 모드 30fps.
- 시뮬레이션은 고정 30Hz로 돌리고 렌더에서 보간한다. 군중 NPC는 5Hz로 갱신하고 애니메이션은 몇 가지 동작을 공유한다.
- 페이지가 숨겨지면 루프와 오디오를 멈춘다. 창 포커스를 잃으면 일시정지 메뉴를 띄운다.
- 프레임당 메모리 할당 0(JS GC 끊김 방지).
- 무거운 디코드는 워커에서(KTX2·meshopt).
- 메뉴, 대화, 사진 앨범처럼 화면이 멈춰 있을 때는 렌더를 멈춘다.

### 6.4 측정과 회귀 방지

- **벤치마크 모드:** 장면마다 고정 카메라 경로를 60초 재생하고 프레임 시간 p50/p95, draw call, 삼각형 수, `renderer.info.memory`, 힙 크기를 JSON으로 출력한다.
- 실측 도구: 크롬 작업 관리자(메모리 사용량과 GPU 메모리 열), DevTools Performance/Memory, Spector.js.
- `performance.measureUserAgentSpecificMemory()`는 COOP/COEP 헤더가 필요하다(Cloudflare Pages에서만 가능).
- **CI(GitHub Actions):** 번들·장면 크기 예산 검사, Rust 코어 단위 테스트, Playwright 스모크 테스트(헤드리스 성능 수치는 참고용, draw call과 메모리 카운터의 회귀만 확인).
- 기준 기기 실측은 마일스톤마다 수동으로 한다. 장면을 20회 오가는 소크 테스트로 메모리 누수를 확인한다.

## 7. 호스팅과 배포

| | GitHub Pages | Cloudflare Pages |
|---|---|---|
| 크기 제한 | 사이트 1GB | 무료: 파일 20,000개, 파일당 25MiB |
| 대역폭 | **월 100GB 소프트 한도** | 공식 수치 재확인 필요(무료 요금제에 대역폭 과금이 없는 것으로 알려짐) |
| 커스텀 헤더(COOP/COEP) | **불가** | `_headers` 파일로 가능 |
| 빌드 | Actions로 배포하면 빌드 횟수 제한 없음 | 무료 월 500회 |

**계산:** 첫 장면까지 15MB × 1만 명 = 150GB. 다른 장면까지 돌아보면 1인당 50MB 이상이 될 수 있다. 유행을 타면 GitHub Pages의 월 소프트 한도를 금방 넘는다.

**권장:**
- 개발 중 미리보기는 GitHub Pages.
- 공개 배포는 **Cloudflare Pages**(또는 GitHub Pages + 에셋만 별도 CDN).
- 파일명에 해시를 넣고 장기 캐시. 장면 에셋은 필요할 때만 받는다.

## 8. 게임 디자인 범위 (MVP 제안)

**컨셉:** 오픈월드 게임 주인공 같은 캐릭터가 겪는 **한국 일상 체험**. 레퍼런스의 재미는 범죄나 혼돈이 아니라 "한국 일상의 디테일"(음식, 웨이팅, 1+1, 잠옷 차림 야식)이다. GTA식 연출(HUD, 시점, 분위기)은 양념으로 쓴다.

**핵심 루프:** 하루 일정 고르기 → 거리·가게에서 활동(미니게임) → 돈(₩)과 시간 소비 → 사진 모드로 장면 찍기 → 하루 끝 "오늘의 한국 생활" 앨범 → SNS 공유.

**MVP 콘텐츠**
- 거리 허브 1곳(홍대입구역 앞 느낌) + 실내 3곳(편의점, 원룸, 삼겹살집).
- 활동 5개(레퍼런스 장면에서 가져옴):
  - 편의점 1+1 고르기(예산 안에서 조합 찾기)
  - 매운 떡볶이 도전(맵기 게이지 관리)
  - 붕어빵 노점(주문, 대기)
  - 빵집 웨이팅(줄 서는 동안 시간 관리, 소소한 이벤트)
  - 삼겹살 굽기(타이밍 미니게임)
- 시스템: 시간(낮/밤), 돈(₩), 기분·포만감, 의상 변경, 세이브.
- **사진 모드 + 앨범:** 고품질 한 장 렌더, 포즈·표정·필터 선택, 이미지 저장·공유. **유행과 게임을 잇는 바이럴 루프.**
- 조작: 키보드+마우스, 게임패드(Gamepad API). 터치는 Phase 3.

**HUD 색상(초안).** 기본은 흰색·검정 중성색이고, 강조색은 한 화면에 2~3개까지만 쓴다. 3D 에셋 텍스처는 이 규칙에서 제외한다. 돈 색을 노랑으로 정한 것은 레퍼런스 HUD(초록 돈 표시)와 차별화하기 위해서다.

| 용도 | 색 |
|---|---|
| 돈(₩) | 노랑 `#FFCC11` |
| 기분·포만감 양호 | 초록 `#55BB44` |
| 경고(배고픔, 맵기 한계) | 빨강 `#FF0045` |
| 정보·안내 | 파랑 `#3355BB` |
| 지하철·물 표시 | 하늘 `#39C5BB` |
| 활동 마커 | 주황 `#FF7E00` |
| 밤 시간대 | 보라 `#660099` |
| 사진 모드 강조 | 분홍 `#FFB4CC` |

## 9. 법적·IP 리스크

- **원작 캐릭터 사용 불가:** 레퍼런스의 주인공은 Rockstar 게임의 기존 캐릭터와 닮았다. **주인공은 반드시 독자 캐릭터**(또는 플레이어가 만드는 아바타)로 한다. 레퍼런스 이미지를 따라 그리거나 학습 자료로 쓰지 않는다.
- **GTA 상표와 트레이드 드레스:** 게임명, 로고, 전용 폰트풍 타이틀, UI 레이아웃과 아이콘을 따라 하지 않는다. 시계·돈 표시나 3인칭 시점 같은 장르 공통 요소는 독자적으로 디자인한다. 공개 타이틀도 독자 브랜드로 정한다(가칭 "My Life in Korea").
- **한국 실존 브랜드:** 레퍼런스에 편의점, 라면, 떡볶이 체인, 소주, 캐릭터 상품 브랜드가 많이 나온다. 전부 **패러디 이름과 독자 로고**로 바꾼다. 스캔한 실물 소품의 라벨도 지운다.
- **레퍼런스 이미지:** 저작권이 있으므로 저장소와 게임에 넣지 않는다. 링크와 텍스트 메모로만 참조한다.
- **라이선스 목록:** 폰트, 에셋, 애니메이션, 스캔 데이터의 라이선스를 `docs/licenses.md`로 관리한다.
- **등급분류:** 국내 공개 형태(무료 웹, 스토어, 유료)에 따라 게임물관리위원회 등급분류 대상인지 확인해야 한다(음주 묘사 포함).

## 10. 로드맵

1인 개발 + Claude Code 보조, 주 20~30시간 기준 대략치. 반실사 캐릭터와 애니메이션 때문에 v0.1보다 늘었다.

| 단계 | 기간 | 산출물 | 통과 기준(게이트) |
|---|---|---|---|
| **Phase 0** 기술 검증 | 2주 | **편의점 실내**(진열대 소품 수백 개, 구운 조명) + **짧은 거리**(군중 30명)를 D와 B(Bevy)로 구현 + 벤치마크 모드 | 최저 기기 30fps, 메모리 400MB 이하, 첫 로딩 15MB 이하, 레퍼런스 1번 장과 나란히 놓고 화질 합의 → **구조 확정** |
| **Phase 1** 버티컬 슬라이스 | 5~6주 | 편의점 + 원룸 + 짧은 거리, 독자 주인공(의상 2벌), 활동 2개, HUD, 사진 모드 초안 | 레퍼런스 2·7번 장 느낌 재현 합의 |
| **Phase 2** MVP | 8~10주 | 허브 + 실내 3곳, 활동 5개, NPC·군중, 낮/밤, 세이브, 사운드, 사진 앨범·공유 | 6장의 예산 전부 충족, 외부 테스터 10명 |
| **Phase 3** 공개 | 3~4주 | 모바일 터치, 저사양 프리셋, 한/영, 성능 다듬기, Cloudflare 배포 | 인스타·스레드 인앱 브라우저에서 동작 확인 |
| **Phase 4** 선택 | — | 장면 추가(성수 골목, 한강, 지하철), 데스크톱판 | — |

MVP까지 약 **4~5개월**.
