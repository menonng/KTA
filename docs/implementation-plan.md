## 1. 목표와 제약

### 1.1 메모리: 목표 300MB, 상한 400MB

- 2026년 측정 자료에 따르면 가벼운 페이지 탭 하나의 상주 메모리는 약 76MB(위키백과)~110MB(해커뉴스)입니다.
- Tom's Guide 테스트에서는 크롬 탭 10개가 952MB였습니다(탭당 약 95MB).
- 따라서 **크롬 탭 5개 ≈ 약 475MB**로 보고, 상한은 그보다 15% 낮은 **400MB**, 목표는 **300MB**로 정합니다.

> ⚠️ 내장 GPU에는 별도 VRAM이 없고 시스템 RAM을 나눠 씁니다. **GPU에 올린 텍스처, 버퍼, 렌더 타깃이 모두 RAM 사용량에 포함됩니다.**

### 1.2 GPU: 외장 그래픽 없이

| 등급 | 예시 기기 | 목표 |
|---|---|---|
| 최저 | Intel UHD 620 (8세대 i5 노트북, RAM 8GB) | 1080p, 렌더 배율 0.67~0.75, **30fps 이상** |
| 표준 | Intel Iris Xe / AMD Radeon 내장(Ryzen 5000U급) | 1080p, 렌더 배율 0.75, **60fps** |
| 표준 | Apple M1 (RAM 8GB) | **60fps** |
| 참고 | 중급 안드로이드·아이폰(인앱 브라우저) | '낮음' 프리셋, 30fps |

### 1.3 CPU

- 표준 기기 60fps에서 **CPU 전체 사용률 25% 이하**(4코어 기준 약 1코어). 절전 모드(30fps)에서는 15% 이하로 합니다.
- 탭이 비활성이거나 일시정지 중이면 사실상 0%로 만듭니다.
- 120/144Hz 모니터에서도 **60fps로 캡**합니다.

### 1.4 로딩

- 첫 플레이까지 다운로드는 **15MB 이하**(압축 기준)로 합니다. 이후에는 이동하는 방향으로 타일을 미리 받습니다.
- 인스타·스레드 인앱 브라우저에서 링크를 누르고 LTE 기준 10초 안에 첫 장면이 뜨는 것이 목표입니다.

### 1.5 제작 방식과 역할

이 프로젝트는 **Claude Code가 전부 만듭니다.** 이 계획서는 사용자가 혼자 보고 피드백하기 위한 문서입니다.

| 담당 | 하는 일 |
|---|---|
| **Claude Code** | Rust·TypeScript 코드 전부, 공개 데이터 → 맵 타일 변환, 절차적 건물·역사·소품·텍스처·간판 생성, 캐릭터·애니메이션(스크립트 기반), 셰이더, 테스트·CI, 미리보기 배포, 스크린샷 기반 자체 검수 |
| **사용자** | 계획과 결과 리뷰·피드백, **실제 노트북(내장 GPU)에서 플레이하고 크롬 작업 관리자로 메모리 확인**, 결정 사항 선택, 일회성 설정 승인(GitHub Pages 켜기, 네트워크 허용, 필요하면 API 키 등록), (선택) 현장 사진 제공 |

**제가 할 수 없는 것과 대안**

| 할 수 없는 것 | 대안 |
|---|---|
| Blender를 화면에서 직접 조작하는 수작업 모델링·스컬프팅 | Blender를 스크립트로 실행(headless)하거나, Rust·Python 코드로 메시를 직접 생성 |
| 사진 촬영, 실물 스캔(포토그래메트리) | 절차적 모델링 + CC0 에셋 라이브러리. 사진을 주시면 디테일 참고에 씀 |
| 로그인이 필요한 웹 서비스(Mixamo 등)를 직접 조작 | CC0 애니메이션 라이브러리(Quaternius), 절차적 애니메이션. AI 생성 서비스는 쓰지 않음(무료 도구만) |
| 실제 내장 GPU에서 성능 측정(작업 환경에 GPU가 없음) | 작업 환경에서는 소프트웨어 렌더링으로 화면·draw call·메모리 카운터를 검사하고, 실제 프레임·메모리는 사용자 기기에서 확인 |
| 세션이 끝나면 작업 환경이 초기화됨 | 작업 단위마다 커밋·푸시, 도구 설치 과정은 환경 설정 스크립트로 저장 |

**리뷰 흐름**

1. 제가 마일스톤 단위로 작업해 브랜치에 푸시합니다.
2. GitHub Actions가 빌드해 **미리보기 링크(GitHub Pages)**로 배포합니다.
3. 고정 카메라 위치의 스크린샷과 벤치마크 요약(메모리, draw call, 삼각형 수)을 함께 보내드립니다.
4. 실제 기기에서 플레이해 보시고 피드백을 주시면 반영합니다.

**현재 작업 환경(확인함):** Rust 1.97, Node 22, Python 3.13, CPU 4코어, RAM 16GB. WASM 타깃, wasm-pack, Blender, KTX2 인코더는 아직 없어서 Phase 0 첫 작업으로 설치합니다.

### 2.4 HUD

레퍼런스의 HUD 두 장(시계, 요일, 돈, 체력)과 같은 **종류의 정보**는 넣습니다. 배치, 폰트, 아이콘, 색은 독자적으로 디자인하고, 돈은 ₩로 표기합니다. 색상은 8장 HUD 색상표를 따릅니다.

### 2.5 주인공 디자인 — 사진과 똑같이 만들 수 있을까요?

**사진 속 인물과 똑같이는 만들 수 없습니다.** 레퍼런스의 주인공은 Rockstar의 GTA 산 안드레아스 캐릭터(CJ)입니다. 얼굴, 체형, 헤어, 이름, 대표 대사까지 그대로 만들면 저작권과 상표를 그대로 침해하게 되고, 패러디라는 이유로 면책되기도 어렵습니다. 유행 짤은 개인이 한두 장 올리는 수준이라 넘어가지만, 배포하는 게임은 다릅니다.

**결정: 흑인, 삭발, 남성이라는 특징만 유지합니다.** 누구에게나 있을 수 있는 일반적인 외형이라 문제가 없습니다. 나머지는 독자적으로 디자인합니다.

- **새로 디자인하는 것:** 얼굴 생김새, 체형, 이름, 말투, 대표 대사. 원작 캐릭터를 닮게 만드는 것을 목표로 하지 않습니다.
- **의상:** 민소매+청바지, 롱패딩, 반바지+흰 양말+슬리퍼, 잠옷처럼 레퍼런스에 나오는 일상복으로 옷장을 구성합니다. 레퍼런스의 웃음 포인트도 대부분 이 옷차림과 상황에서 나옵니다.
- **표현 원칙:** 고정관념적인 과장 없이, 자연스럽고 매력 있는 인물로 디자인합니다.
- **제작:** 6.5의 도구로 초안을 만들고, 스크린샷 리뷰를 여러 번 거쳐 확정합니다.

## 3. 맵: 범위와 구현 방식

### 3.1 범위

- **서울 + 김포 + 인천공항**, 지상과 지하(지하철역, 지하상가, 공항철도) 모두 포함합니다.
- **김포는 김포공항 일대로 정했습니다.** 국내선·국제선 터미널, 공항 쇼핑몰(라떼몰 김포공항), 김포공항역(5·9호선·공항철도·김포골드라인) 주변입니다. 김포공항은 대부분 서울 강서구에 있습니다.
- 인천공항은 서울과 땅으로 바로 붙어 있지 않습니다(인천 서구와 영종대교를 지나야 합니다). 그래서 **공항철도·공항버스 탑승으로 연결하는 별도 구역**으로 둡니다. 탑승 시간이 자연스러운 로딩 구간이 됩니다.

### 3.5 지하 구현

- **역사:** 서울 지하철역은 구조 유형(상대식/섬식 승강장, 지하 1~4층, 환승역)이 반복됩니다. **역 템플릿 6~8종**을 만들고 Rust가 역별 파라미터(출구 수, 층수, 노선 색)로 조립합니다. 대표 역(홍대입구, 강남, 서울역, 김포공항, 인천공항)은 수작업으로 만듭니다.
- **터널·객차:** 터널은 반복 모듈 몇 개를 이어 붙입니다. 객차 내부는 노선별로 색만 바꿉니다.
- **지하상가:** 대표 3~5곳만 만들고, 상점 칸을 모듈로 반복합니다.
- **참고 자료:** 카카오맵 3D·실내 지도와 이미지는 **구조를 눈으로 파악하는 용도**로만 씁니다. 형상은 공개 자료(브이월드 실내공간정보, 역사 구내 안내도)를 기준으로 만들고, 사용자가 찍은 사진이 있으면 디테일 참고에 씁니다.
- **메모리:** 지상과 지하는 서로 보이지 않습니다. 지하에 있을 때는 지상 상세(R0·R1)를 내리고, 그 예산을 역사 내부에 씁니다. 계단·출구처럼 전환하는 구간만 둘 다 일부 올립니다(4.6 피크 시나리오).

## 4. 메모리 예산 계산

### 4.1 원칙: 메모리는 맵 크기가 아니라 시야 반경 안의 밀도로 정해집니다

스트리밍을 하면 메모리에 올라가는 것은 **카메라 주변 몇 km 안의 데이터**뿐입니다. 그래서 900km²의 1:1 서울이든 25km²의 재구성 맵이든, 가장 빽빽한 동네에서 한 번에 보이는 양이 예산을 결정합니다. 맵 크기는 다운로드 총량과 제작량에만 영향을 줍니다.

**기준 밀도:** 서울 평균은 약 1,000동/km²(60만 동 ÷ 605km²)지만, 다세대 주택가나 상가 밀집 지역은 훨씬 빽빽합니다. 예산은 최악의 경우인 **5,000동/km²**로 잡습니다.

### 4.2 단순 구현 vs 최적화 (얼마나 줄여야 하나)

| 항목 | 단순하게 구현하면 | 최적화 후 | 줄이는 배율 |
|---|---|---|---|
| 건물 지오메트리 (반경 1.5km, 3만 5천 동을 전부 상세 1,500tri로) | 5,300만 tri × 26B ≈ **1.4GB** | 약 19MB (LOD 링, 4.3) | **약 74배** |
| 건물 텍스처 (가까운 2,500동에 고유 1K PBR PNG) | 동당 16MB × 2,500 ≈ **40GB** | 파사드 트림시트 공유 약 27MB | **1,000배 이상** |
| 렌더 타깃 (1080p 원본 해상도, HDR RGBA16F, MSAA 4x, 2K 그림자) | 약 **157MB** | 약 29MB | **약 5.4배** |
| 건물 데이터 다운로드 (건물마다 glTF 메시) | 동당 약 40KB → 60만 동 ≈ **24GB** | 동당 40바이트 레코드 → **약 24MB**(압축 시 약 10MB) | **약 1,000배** |

**결론:** 일반적인 방법으로는 수 GB가 필요합니다. 300MB 안에 넣으려면 **LOD 링, 텍스처 공유, 절차적 생성, 렌더 해상도 관리**를 전부 적용해야 합니다. 이것이 계산·데이터 처리를 Rust에 맡기는 이유입니다(5장).

### 4.4 항목별 예산 (목표 300MB)

### 4.5 숨은 메모리 함정 (반드시 처리)

| 함정 | 대응 |
|---|---|
| Three.js는 GPU에 올린 뒤에도 정점 배열·KTX2 밉맵 배열을 JS 힙에 그대로 들고 있음 | 업로드 콜백에서 배열 참조 해제. Rust가 만든 메시는 WASM 메모리 뷰로 올린 뒤 작업 공간을 재사용하므로 **JS 쪽 사본이 생기지 않음** |
| 캔버스 백버퍼가 화면 해상도로 2~3장 잡힘 | 캔버스를 내부 해상도로 만들고 CSS로 확대 |
| 고DPI 화면에서 devicePixelRatio 2.0 | 픽셀 비율 상한 1.0~1.25 |
| WASM 메모리는 한 번 늘면 줄지 않음 | 초기값 = 최댓값 고정, 아레나·풀 할당 |
| 장면 전환 중 두 장면이 동시에 올라감 | 이전 장면을 먼저 해제한 뒤 로드 |
| 디코드한 오디오 PCM이 큼 | 긴 소리는 스트리밍 |

|---|---|---|---|---|---|
| 낮음 | 0.67 | 512 | 절반 | 끔 | 약 240MB |

### 4.8 렌더·CPU 예산

- **draw call 300 이하/프레임.** WebGL은 호출당 CPU 비용이 커서 CPU 사용률과 바로 연결됩니다. 블록 단위 병합(HLOD)과 인스턴싱으로 줄입니다.
- 화면 안 삼각형 60만 이하.
- 실시간 광원 2~4개, 캐릭터 주변에만 그림자맵 1장.
- 동적 해상도: 프레임 시간 p95가 기준을 넘으면 렌더 배율을 0.67까지 자동으로 낮춥니다.
- CPU: 시뮬레이션 고정 30Hz + 렌더 보간, 먼 NPC는 5Hz 갱신, 절차적 생성은 **프레임당 2ms 작업 예산**으로 나눠서 처리합니다(끊김 방지).
- 탭이 숨겨지면 루프와 오디오를 멈추고, 메뉴처럼 화면이 멈춰 있을 때는 렌더를 멈춥니다.

## 5. 구조: Rust 중심 최적화

### 5.1 왜 이 구조인가

최적화를 위해 Rust를 골랐다면, **CPU를 쓰는 일은 전부 Rust에서 하고 JS는 최소한만** 하는 것이 맞습니다. 동시에 "링크를 눌러 바로 플레이"와 "한글 UI"를 지키려면 웹에서 돌아야 합니다. 그래서 다음처럼 나눕니다.

| 계층 | 맡는 일 |
|---|---|
| **Rust (WASM)** | 스트리밍, 절차적 도시·역사 생성, 컬링, LOD 선택, 인스턴스 버퍼 작성, 물리, 시뮬레이션(NPC·교통·경제·시간), 애니메이션 샘플링, 세이브 |
| **Three.js (TS)** | Rust가 만든 버퍼를 GPU에 제출, 머티리얼·셰이더, 후처리. **씬 그래프는 최소한으로**(도시 건물을 Object3D로 만들지 않음) |
| **HTML/CSS** | HUD, 메뉴, 대화, 사진 앨범(한글 텍스트는 브라우저가 처리) |

### 5.2 Rust가 맡는 최적화

| # | 시스템 | 내용 | 효과 |
|---|---|---|---|
| 1 | 절차적 도시 생성기 | 건물 1동 = **40바이트 레코드**(외곽선 꼭짓점 델타, 높이, 층수, 용도, 지붕 형태, 파사드 시드, 간판 슬롯). 메시를 WASM 메모리에 직접 생성 → GPU 업로드 → 작업 공간 재사용 | 다운로드 약 1,000배 감소, JS 사본 0 |
| 2 | 스트리밍 스케줄러 | 타일 쿼드트리, 우선순위 큐(거리, 시야, 이동 방향 예측), 프레임당 2ms 작업 예산 | 끊김 없는 로딩 |
| 3 | 오클루전 컬링 | 256×128 저해상도 깊이 버퍼에 가까운 큰 건물을 **SIMD128로 래스터화**해 가려진 블록 제외 | 도심 지상 시점에서 draw call·삼각형 대폭 감소 |
| 4 | LOD·HLOD 선택 | 링별 표현 결정, 블록 병합 메시 관리 | draw call 감소 |
| 5 | 인스턴스 버퍼 작성 | 보이는 소품·NPC·차량 목록을 SoA 버퍼로 만들어 Three.js InstancedMesh/BatchedMesh에 그대로 업로드 | 개체별 JS 호출 0 |
| 6 | 역사 조립기 | 역 템플릿 + 역별 파라미터로 지하 공간 생성 | 338개 역을 템플릿 6~8종으로 커버 |
| 7 | 군중·교통 시뮬레이션 | 2,000명 SoA, 먼 개체는 추상화 | CPU 절약 |
| 8 | 애니메이션 샘플링 | 뼈 행렬을 SIMD로 계산 → GPU 스키닝 | JS 부하 제거 |
| 9 | 데이터 포맷 | 자체 바이너리 타일(양자화 + 델타 + 가변 길이 정수) → 브라우저 내장 압축 해제(DecompressionStream) 사용 | 디코더 코드 0바이트 |
| 10 | 메모리 규율 | WASM 32MB 고정, 아레나·풀, **게임 루프 중 할당 0**(디버그 빌드에서 할당 횟수 검사) | 메모리 증가·GC 끊김 없음 |

**빌드 설정:** LTO, `codegen-units=1`, `panic=abort`, wasm-opt `-O3`, SIMD128 활성화. 목표 크기 1.5MB(gz) 이하.

### 5.4 Rust ↔ JS 경계 원칙

- 프레임당 호출 1~3회(`step`, `drain_events`, `upload_list`). 개체 단위 호출은 금지합니다.
- 버퍼는 Rust가 소유하고 JS는 `Float32Array`·`Uint16Array` 뷰로 읽습니다. WASM 메모리가 고정 크기라 뷰가 무효화되지 않습니다.
- 에셋(메시·텍스처)은 Rust가 `asset_id`로만 다룹니다.

### 5.5 구조 후보 비교 (요약)

| 후보 | 판단 |
|---|---|
| A. Rust만, 네이티브 | 성능은 최고지만 설치가 필요해 SNS 링크 실행이 불가능합니다. 나중에 데스크톱판으로 고려합니다 |
| B. Bevy → 웹 | 렌더 기능은 풍부하지만 wasm이 크고(수 MB~10MB대), WebGL2/WebGPU를 따로 빌드해야 하고, 웹에서 단일 스레드이며, 한글 UI가 불리합니다 |
| B'. Rust + 자체 렌더러(wgpu/WebGL2) | 최적화 상한은 가장 높지만 렌더러를 직접 만들어야 합니다. **Phase 0에서 Three.js 오버헤드가 기준을 넘으면 전환하는 예비안**입니다 |
| C. Three.js 단독 | Rust를 쓰지 않아 최적화 요구에 맞지 않습니다 |
| **D. Rust 중심 + Three.js 제출 (권장)** | 위 5.1~5.4 |
| E. Godot 웹 | 엔진 런타임 전체를 받아야 해서 초기 다운로드와 메모리 기준선이 큽니다 |

## 6. 에셋 파이프라인

### 6.1 흐름

```
[공개 데이터] OSM·브이월드·서울 열린데이터 → kta-datatool(Rust) → 타일(.bin, 건물 40B/동)

```

### 6.4 캐릭터·애니메이션 범위 (MVP)

- 주인공 1명(흑인·삭발·남성, 나머지 독자 디자인), 의상 6~8벌: 민소매+청바지, 롱패딩, 반바지+흰 양말+슬리퍼, 잠옷 2종, 외출복.
- NPC: 체형 3종 × 의상·헤어 조합. 특수 NPC: 택시 기사, 노점 상인, 편의점 직원, 전도하는 사람.

- 얼굴 블렌드셰이프 6~8개: 눈 감기, 씹기, 미소, 매워하기, 놀람, 고민.

## 8. 게임 디자인 범위 (MVP)

**컨셉:** 오픈월드 게임 주인공 같은 인물(독자 캐릭터)이 한국에서 겪는 **일상 체험**입니다. 레퍼런스의 웃음 포인트는 범죄가 아니라 "한국 일상의 디테일"(편의점, 웨이팅, 택시 기사, 길거리 전도, 노래방, 롱패딩)입니다.

**핵심 루프:** 하루 일정 → 이동(걷기·지하철·택시) → 활동(미니게임) → 돈(₩)·시간 소비 → 사진 모드로 장면 찍기 → 하루 끝 "오늘의 한국 생활" 앨범 → SNS 공유.

**MVP 콘텐츠**
- 구역: 인천공항 T1 입국장(시작) → 공항철도 → 홍대입구(지상 + 역사 지하) → 원룸.
- 실내: 편의점, 원룸(화장실 포함), 노래방, 삼겹살집.
- 활동 6개: 편의점 1+1 고르기, 매운 떡볶이 도전, 붕어빵 노점, 노래방 점수, 삼겹살 굽기, 지하철 자리 잡기.
- 랜덤 이벤트: 길거리 전도, 택시 기사 잔소리.
- 시스템: 시간(낮/밤), 날씨(눈 포함), 돈(₩), 기분·포만감, 의상, 세이브.
- **사진 모드 + 네컷 사진 프레임:** 레퍼런스의 네컷 사진처럼 4컷 프레임으로 저장할 수 있게 합니다. **유행과 게임을 잇는 바이럴 루프**입니다.

**HUD 색상(초안).** 기본은 흰색·검정 중성색이고, 강조색은 한 화면에 2~3개까지만 씁니다. 3D 에셋 텍스처는 이 규칙에서 제외합니다.

| 용도 | 색 |
|---|---|
| 돈(₩) | 노랑 `#FFCC11` |
| 기분·포만감 양호 | 초록 `#55BB44` |
| 경고(배고픔, 맵기 한계) | 빨강 `#FF0045` |
| 정보·안내 | 파랑 `#3355BB` |

## 10. 법적·IP 리스크

- **원작 캐릭터:** CJ 등 Rockstar 캐릭터의 외모·이름·대사(예: "Ah shit, here we go again")를 쓰지 않습니다. 주인공은 독자 디자인입니다(2.5).
- **GTA 상표·트레이드 드레스:** 게임명, 로고, 전용 폰트풍 타이틀, HUD 레이아웃·아이콘을 따라 하지 않습니다. "GTA 시리즈 감성 기반" 표기는 영향을 받았다는 의미로만 씁니다.
- **실존 브랜드:** 7장 원칙(패러디 이름, KIPRIS 확인). 디자인은 A(그대로)로 결정했고 위험을 인지하고 진행합니다.
- **지도 데이터:** 3.6 원칙(지도 서비스 데이터 추출·트레이싱 금지, 공개 데이터 라이선스 준수, 보안시설 제외).
- **레퍼런스 이미지:** 저장소와 게임에 넣지 않습니다.
- **라이선스 관리:** `docs/licenses.md`(데이터, 폰트, 에셋, 애니메이션, 스캔).
- **비영리:** 상업 목적이 없어 상표·부정경쟁 위험은 낮아지지만, 로고 그림의 저작권과 브랜드 이미지 훼손(패러디 브랜드 매장을 터는 연출 등)에 따른 신고 위험은 남습니다. 범죄 미션은 업종 이름만 붙은 일반 가게에서 일어나게 합니다.
- **등급분류:** 개인이 비영리로 단순 공개하는 게임은 등급분류가 면제됩니다(2019년 9월 시행령). 단 **청소년이용불가 기준에 해당하는 내용이 있으면 면제되지 않습니다.** 폭력·범죄 표현은 15세 수준(과도한 유혈, 마약, 성적 묘사 없음)으로 유지하는 것을 기본으로 하고, 그 이상으로 갈 경우 국내 공개 전에 게임물관리위원회 심의를 받습니다.

## 11. 로드맵

제가 만들고 사용자가 리뷰하는 방식이라 기간보다 **리뷰 게이트**를 기준으로 나눕니다. 각 단계 끝에 미리보기 링크와 스크린샷을 드리고, 피드백을 반영한 뒤 다음 단계로 넘어갑니다.

| 단계 | 제가 만드는 것 | 사용자 리뷰 포인트 |
|---|---|---|
| **Phase 0** 기술 검증 | 도구 설치, 빌드·배포 파이프라인, 홍대입구 일대 지상 1블록(공개 데이터 → 절차적 생성) + 역사 지하 1곳(템플릿) + 편의점 실내, 벤치마크 모드. D와 B(Bevy) 비교 측정 | 실제 노트북에서 30fps 이상인지, 크롬 작업 관리자 메모리가 300MB 안팎인지, 레퍼런스와 화질 비교 → **구조 확정** |
| **Phase 1** 버티컬 슬라이스 | 홍대입구 지상·지하 완성, 원룸, 독자 주인공(의상 3벌), 활동 2개, HUD, 사진 모드 초안 | 주인공 디자인, 레퍼런스 느낌 재현, 조작감 |
| **Phase 2** MVP | 인천공항 T1 입국장 → 공항철도 → 홍대, 실내 4곳, 활동 6개, NPC·교통, 날씨, 세이브, 사운드, 네컷 사진 | 하루 플레이 흐름, 재미, 오래 플레이할 때 메모리(피크 시나리오 4.6) |
| **Phase 3** 공개 준비 | 모바일 터치, 저사양 프리셋, 한/영, 브랜드 KIPRIS 확인 목록, 공개 배포 설정 | 휴대폰 인앱 브라우저 동작 |
| **Phase 4** 확장 | 3.4 표 순서로 구역 추가, 김포공항, 인천공항 T2, 지하상가 | 구역마다 메모리 재확인 |

진행 속도를 좌우하는 것은 코드 작성보다 **에셋 품질을 맞추는 반복**과 **실기기 확인 왕복**입니다. 특히 캐릭터는 리뷰가 여러 번 필요할 것으로 봅니다.
